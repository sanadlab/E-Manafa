retrieves the energy to attribute to a method that ran between two timestamps.

With power rails, this is the measured energy of the CPU rails in the interval (see PowerRailsTrace.method_rails). class manafa.parsing.perfettoEnergyCalculator.PowerRailsTrace(rails, monotonic_to_epoch_s=0.0, source='power rails', consumers=None)[source]

Power rail energy counters of a Perfetto trace, as time series.

If the trace has no power rails but has energy consumers of the PowerStats HAL for the CPU clusters, the consumers are used in the place of the rails (source = CONSUMERS). A consumer has the name consumer.<type>.<ordinal>.<name>, for example consumer.cpu_cluster.0.CPUCL0.

Power rail counters are cumulative energy values, so the energy of a time interval is the counter at the end minus the counter at the start. The counters are sampled every battery_poll_ms. Between two samples the value is linearly interpolated, which means that an interval shorter than the sampling period gets the mean power of that period.

All times are Unix epoch seconds on the device clock.

rails

rail name -> (times, joules), two lists of the same length.

Type:

dict

monotonic_to_epoch_s

seconds to add to a CLOCK_MONOTONIC time of the device (the clock of ART method traces) to get epoch seconds.

Type:

float

source

RAILS or CONSUMERS: where the series of rails come from.

Type:

str

consumers

energy consumers of the trace, in the format of rails.

Type:

dict

manafa.parsing.perfettoEnergyCalculator.calculate_memory_stats(trace_file, app_package=None)[source]

Calculate system memory statistics from Perfetto trace.

Returns min, max, and average for system memory counters.

Attribution of the energy of the CPU power rails to threads and processes.

The CPU rails give the energy of each CPU cluster, not of each process. The scheduler events of the same Perfetto trace give the time that each thread ran on each CPU. Between two rail samples, a thread gets the part of the energy of a cluster that is equal to its part of the run time on the CPUs of that cluster.

The energy of an interval where no thread ran on a cluster is not attributed.

On-device mode and MCP server

On-device mode: the device records a session with no computer, and E-MANAFA analyses it later.

emanafa ondevice install put the recorder and the Perfetto configs on the device emanafa ondevice start [-pm MODE] [-a APP] [–trace-methods am|perf] emanafa ondevice stop emanafa ondevice export [DIR] copy the recorded sessions to the computer emanafa ondevice analyze [DIR] results of each recorded session, as in the normal mode emanafa ondevice run -s SECONDS all the steps in sequence emanafa ondevice status | clean

After install, start and stop can also be given in a shell on the device, with the USB cable disconnected: sh /data/local/tmp/emanafa/manafa.sh start energy

The recorder (resources/ondevice/manafa.sh) uses the same Perfetto configs and does the same steps as the E-MANAFA services, so the two modes give the same kind of results.

MCP server of E-MANAFA: an LLM client can record sessions and read their results.

The results directory (default: emanafa_ondevice, or the EMANAFA_RESULTS_DIR variable) has the sessions that emanafa ondevice export copied from a device. The tool record_session adds new sessions to it.

Each tool is a function of this module, so it can also be used with no MCP client.

Sunburst diagram

Animated sunburst of an app’s call graph, coloured by energy.

Each ring is one call level, so a method that calls x and y contains x and y. A sector is one call path: all the invocations of a method that have the same callers. Two more views have 3 levels (package, class and method): one for all the code, and one for the app only, with the calls of each method below it. The page also has a search box, buttons for the number of levels and a ranked list of the methods that consume the most energy in their own code. A node’s value is its inclusive energy, which means a caller always covers at least the sum of its callees, and the colour scale follows that value: the darker the sector, the more energy the call and everything below it consumed.

The call graph comes from the AM trace CSV (name, ts, dur, depth) recorded with –trace-methods am. The energy comes from the power rails that the session attributes to methods (the CPU rails): a frame gets the energy that these rails consumed while it was running. Sessions without that time series fall back to the session total, attributed in proportion to time on the stack.
